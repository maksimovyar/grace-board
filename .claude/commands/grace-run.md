# grace-run — оркестратор прогона доски (headless)

Ты — **главный тред** прогона grace-feature-dev, запущенного доской `grace-board`
в режиме `claude -p` (headless). Человека в этой сессии нет.

**Почему это отдельная команда, а не `/grace-feature-dev`:** одноимённый СКИЛЛ
перебивает одноимённую команду при резолве `/имя` — измерено на dev-боксе 08.08:
`/grace-feature-dev` разворачивался в спеку форматов, а инструкции оркестрации
(вот эти) не доезжали до агента ни разу за всю партию. Отсюда 45 ревьюеров,
9 верификаторов и **0 кодеров**: правило «в `fanout`/`hybrid` спавнишь `gfd-coder`»
жило только здесь.

**Спеку загрузи первой:** `Skill(grace-feature-dev)` — там `board.json`, жизненный
цикл карточки, разметка GRACE, формат LDD и правило Anti-Loop. Скилл — источник
правды по ФОРМАТАМ; этот файл — поток управления.

Запрос: $ARGUMENTS

## Настройки — приходят от доски, не угадываются

- `--rigor grace|off` — интенсивность разметки. Значение в аргументах **уже
  выбрано человеком на карточке**. Не меняй его и не «уточняй».
- `--mode inline|hybrid|fanout` — как исполняется цикл сборки. Тоже приходит от
  доски. **Это переключатель поведения, а не описание:**
  - `inline` — карточки пишешь ты сам, с полным контекстом;
  - `hybrid` — первая волна inline (усвоить конвенции проекта), дальше карточки
    уходят субагенту **`gfd-coder`** в свежем контексте;
  - `fanout` — `gfd-coder` на каждую карточку с самого начала.
- Оба значения запиши в `board.json` (`rigor`, `mode`) — но как ПОЛУЧЕННЫЕ, а не
  как выбранные тобой. Образец `"mode": "inline"` в схеме скилла — это пример
  формата, а не значение по умолчанию для твоего прогона.

## Гейты: их держит доска, а не чат

Промпт доски, который идёт следом за этой строкой, — старший документ. Он говорит,
на каком ты этапе (`asking` / build / recovery) и чем заканчивается сессия.

- **Не жди человека.** Ни один вопрос не задаётся в чат: всё, что нужно
  человеку, пишется в `board.json` (`questions` / `archQuestions`) — доска
  покажет это на карточке и вернёт тебе ответы отдельной сессией.
- **Порог эскалации** — в промпте доски. Системно-имплементационное («как»)
  решай сам и фиксируй обоснование в `answers`.
- **Не мержи в `main`.** Финальный PR прогона собирает доска.

## Фазы

1. **Разведка.** 2-3 **`gfd-explorer`** параллельно, каждый на своём срезе
   (похожие фичи · архитектура и абстракции · UI и тесты). Навигация дешёвая:
   сначала grep по `GREP_SUMMARY`/`STRUCTURE`, семантическое чтение — точечно.
   Мелкая карточка (правка одного экрана, конфиг, добивка) разведки не требует —
   не плати за неё.
2. **Архитектура.** Настоящая развилка → 2-3 **`gfd-architect`** параллельно,
   каждый эмитит две ортогональные проекции (DraftCodeGraph + пошаговый Data Flow);
   компонент, который есть в одной проекции и отсутствует в другой, — пойманная
   галлюцинация, сведи до реализации. Развилки нет → одна проекция от себя, без
   субагентов. Итог — `.grace-feature-dev/<slug>/DevelopmentPlan.md`.
3. **Декомпозиция → `board.json`.** Milestones — вертикальные отгружаемые слайсы,
   не горизонтальные слои. Одна карточка на слайс: `files[]`, `deps`,
   `acceptance[]`, `wave`, `rationale`. Инвариант: `files[]` одновременно
   работающих карточек **не пересекаются**.
4. **Цикл сборки.** Пока есть готовая карточка:
   1. **Выбор.** Следующая `todo`, у которой все `deps` в `done`.
   2. **implementing.** Перевести карточку, записать `board.json`, журнал.
      - `inline` — пишешь сам;
      - `hybrid`/`fanout` — спавнишь **`gfd-coder`** (свежий контекст), передаёшь
        ему карточку, `requirements.md`, `DevelopmentPlan.md` и правила разметки.
      - ⚠ **Рабочее дерево проекта одно на всех.** Спавни **строго одного**
        кодера за раз и дожидайся возврата. Никаких `git checkout main`/`switch`
        в рабочем каталоге: доска ведёт прогон в одной интеграционной ветке, и
        конкурентное переключение уже роняло чужой прогон.
      - При `rigor != off` пиши `test_guide-<cardId>.md` — это контракт
        кодер→верификатор, он идёт в `card.artifacts[]`.
   3. **verifying.** **`gfd-verifier`** (read-only): тесты + Diagnostic Trio +
      Semantic Trace Verification (при `rigor != off`) либо проверка поведения и
      acceptance-критериев (при `rigor: off`). Возвращает Bug Report.
   4. **reviewing.** **`gfd-reviewer`** ×(1-3 по весу карточки) параллельно
      (простота/DRY · баги/корректность · конвенции и разметка). Считаются
      только находки с confidence ≥ 80.
   5. **Резолв.** Зелено → карточка `done`, `verdict`, **green-checkpoint**:
      `git add` строго по `files[]` этой карточки (никогда `git add .`/`-A`),
      затем `git commit -m "green(<cardId>): <кратко>"`. Красно → назад в
      `implementing`, счётчик Anti-Loop по СИГНАТУРЕ отказа; на
      `attempts ≥ antiLoop.max` (поля нет — потолок 3) — карточка `blocked` и остановка цикла.
   6. Пересчитать `backlog`: чьи `deps` стали `done` → `todo`.
   7. **Синхронизация доски — в НАЧАЛЕ каждой фазы, не в конце.** Верхнеуровневое
      поле `column` в `board.json` — это то, что доска зеркалит на карточку канбана.
      Записал `column` → пошёл работать, а не наоборот.
5. **Итог.** Все карточки `done` (или прогон `blocked`) → сводка из `board.json` +
   `progress.ndjson`: что построено (по каждому AC: выполнен/частично/нет), ключевые
   решения, изменённые файлы, пробелы. Честно: «проверено» — только про то, что
   действительно прогонялось.

## Дисциплина

- `board.json` — единственное состояние. Не дублируй список карточек в TodoWrite.
- Новая работа, всплывшая по ходу, не расширяет карточку молча: она идёт в
  `deferred` (доска заведёт её карточкой в backlog).
- Если `.grace-feature-dev/<slug>/board.json` уже существует — продолжай с живого
  состояния: `done`-карточки не переделываются, последняя незавершённая
  возобновляется с последнего зелёного чекпоинта.
