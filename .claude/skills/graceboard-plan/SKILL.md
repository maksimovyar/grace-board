# graceboard-plan — декомпозиция требований в прогон

Цепочка: **graceboard-plan** (границы этапа и карточек) → **graceboard-card**
(механика создания) → **graceboard-run** (сборка DAG). Соседей вызывай, не дублируй:
нейминг темы, лимит описания, «править только в Backlog» — там. Предметную область
(стек, команды, инварианты, роли, константы) бери из `.grace/project.md` репозитория.

**Словарь (дальше только эти слова).** **Этап** ≡ прогон ≡ один план-файл ≡ ветка
`autodev/plan-<id>` ≡ один PR. **Карточка** — единица внутри этапа, режется
**вертикально** (сценарий целиком, не слой). **Волна** (`t1/t2/t3`) — шаг внутри
карточки, его планирует сам конвейер. **Фаза** — `домен` либо `поверхности`;
необязательное деление этапа, см. Ш2b.

## Два такта, между ними гейт

| Такт | Шаги | Что появляется |
|---|---|---|
| 1 | Ш0–Ш6 | план-файл(ы) в целевом репо; **на доске — ничего** |
| — | Ш7 | **СТОП.** Человек читает, отвечает в том же файле, решает объём выноса |
| 2 | Ш8 | карточки в Backlog + собранные прогоны |

Скопируй чек-лист в свой ответ и отмечай по ходу:

```
Такт 1: [ ] Ш0 конфиг  [ ] Ш0b доска+дизайн  [ ] Ш0c готовность входа
        [ ] Ш1 источники  [ ] Ш1b инвентаризация (если этапов ≥2)
        [ ] Ш2a этапы  [ ] Ш2b карточки  [ ] Ш3 поля  [ ] Ш4 симуляция ask
        [ ] Ш5 DAG+files  [ ] Ш6 файл + самопроверка
ГЕЙТ:   [ ] человек утвердил
Такт 2: [ ] коммит плана  [ ] .grace дополнен  [ ] карточки  [ ] сверка
        [ ] preflight  [ ] прогон  [ ] карта обновлена
```

## Порядок действий

**Ш0.** Прочитай `.grace/project.md` и `.grace/local.md` целевого репо. Файла нет →
**СТОП**, предложи завести по `~/Projects/grace-board/docs/PROMPT-grace-config-rollout.md`.

**Ш0b. Доска и источник дизайна — до нарезки, не после.**
```bash
node ~/.claude/bin/gb.mjs board --project <ПРОЕКТ>
node ~/.claude/bin/gb.mjs board --project <ПРОЕКТ> --column backlog
```
- «cannot reach board» → подними: `cd ~/Projects/grace-board && node server.js &`;
- пустой ответ с подсказкой «no card matched --project» = **опечатка в имени
  проекта, а не чистая доска**; возьми значение из списка в подсказке;
- незакрытые карточки этого модуля и хвосты прошлых прогонов — **материал этого
  плана, а не повод завести дубль**; выпиши id, на Ш8 они берутся с доски;
- карточка в любой колонке кроме `backlog`/`ready` = проект занят: новый прогон
  встанет в очередь (WIP=1 на проект);
- строка `## Дизайн` в `CLAUDE.md` проекта обязательна. Нет — заведи сейчас: иначе
  preflight поднимет блокер `design-source`, а карточки с экранами режутся вслепую.

**Ш0c. Готовность входа.** Четыре признака: источники названы и доступны · цель
формулируется одним сценарием · известно, кто пользователь и что он делает · известно,
чем меряется «готово». Провал двух и более → **СТОП**, задай вопросы одним пакетом.
Нарезка сырых требований даёт вопросы в рантайме, а не план.

**Ш1. Реестр источников.** Таблица «источник → приоритет → что в нём устарело».
Каждое расхождение разреши **письменно** и запиши в план-файл. Источник правды под
прогон один, и создаёшь его ты.

**Ш1b. Инвентаризация репозитория** — только при этапах ≥2, порядок в `stages.md`.

**Ш2a. Сколько этапов в объёме.** Этап = прогон, их может быть и 1, и 5–8.
- **один** → карта не нужна, её разделы («что готово / чего нет / модель данных»)
  вставь прямо в план прогона, переходи к Ш2b;
- **два и больше** → **СНАЧАЛА прочитай `stages.md`** (карта модуля, порядок этапов,
  deferred, сколько прогонов выносить) — без него нарезка на этапы неверна;
- **карта уже есть** → прочти её и возьми следующие незакрытые этапы.

**Ш2b. Нарезка этапа на карточки.** Сначала ось разреза (вертикальная), потом — нужно
ли вообще делить этап на фазы; правила ниже. Целевое число карточек на этап — **3–5**.

**Ш3. Поля будущих карточек.** Пустых быть не должно — карточку заводит агент, доска
проверяет строго (см. «Строгость по автору»): `outOfScope`, `acceptance`, `contract`,
`sources`, `files[]`. Плюс три связки:
- `--req-link <путь к план-файлу>` — на **каждой** карточке, это её источник правды;
- `--design-link <макет>` — на каждой карточке, у которой есть экран. Нет макета — это
  вопрос на Ш7, а не «агент придумает»;
- `--type` — тип карточки (см. «Тип карточки» ниже). Это ЕДИНСТВЕННАЯ ручка исполнения:
  `--rigor`, `--model`, `--build-mode`, `--autonomy` с карточки сняты, доска выводит их
  из типа сама. `dependsOn` тоже не здесь — он задаётся на сборке прогона (`--stage`).

**Ш4. Симуляция ask.** По каждой карточке: «на чём здесь агент остановит прогон?».
Порог доски (`launchAskFunctional` / `launchAskArchitecture` в `server.js`): человека
спрашивают, только если решение (а) меняет поведение продукта или объём, (б) имеет
внешние последствия (стоимость, vendor lock-in, юридика, необратимость, форма данных
в контракте), (в) по нему может быть мнение у не-разработчика. Всё «как» (структура
файлов, имена, паттерны, глубина тестов) агент решает сам — не моделируй.
- **бизнес-вопрос** → в «Открытые вопросы» плана, **2–3 варианта с помеченным
  дефолтом**: человек отвечает буквой;
- **технический** → ответь **сейчас** в `contract` / `description`.

**Ш5. DAG.** Он же — последняя проверка нарезки: форма графа показывает ось разреза.
- **выпиши граф и посчитай длину самой длинной цепочки.** 4+ звеньев в ряд → вернись
  на Ш2b, резано по слоям. Здоровая форма — веер, глубина ≤ 3;
- **сложи `files[]` всех карточек и найди пересечения.** Один файл в двух карточках →
  склей их (или перенеси файл целиком в одну). Это не «оптимизация», а тот же дефект
  оси: доска всё равно выстроит их в очередь, но заплатишь дважды за один контекст;
- `files[]` — **реальные относительные пути репозитория** (`src/api/cases.ts`), не
  описания: по ним доска держит пересекающиеся карточки в очереди друг за другом;
- `dependsOn`, записанный при создании карточки, **перезаписывается при сборке
  прогона**; единственный работающий способ — `--stage <id>:<dep1>,<dep2>` в
  `graceboard-run`. Держи зависимости в план-файле, а не только в поле карточки;
- цикл сервер отвергнет (400 `dependency cycle`), но лучше не доводить.

**Ш6. Запиши план-файл(ы), затем самопроверка — три прохода:**
1. **покрытие** — у каждого пункта каждого источника есть адрес: карточка или строка
   «НЕ входит». Непокрытых пунктов нет;
2. **заглушки** — в плане нет «и т.п.», «аналогично карточке N», «детали в §X».
   `TBD` допустим **только** в `contract`;
3. **стыковка** — поле/эндпоинт, который потребляет карточка B, порождается карточкой
   A и записан в её `contract`; расхождение имён = вопрос в рантайме.

Провал любого прохода → правь план, гейт не начинается. Затем покажи пути файлов.

**Ш7. СТОП — гейт утверждения.** На доске не создаётся ничего, ни одной карточки, ни
черновой. Человек читает файл, отвечает на «Открытые вопросы» правкой файла или
репликой, при необходимости меняет разбивку.

Этапов больше одного → **спроси, сколько прогонов вынести на доску сейчас** (один /
несколько / все), приведя расклад из `stages.md`. Сам за человека не решай.

**Ш8. После утверждения — строго в этом порядке:**
1. **закоммить план-файл(ы) и карту** в `main` целевого репо: интеграционная ветка
   прогона снимается с `main`, и карточка обязана видеть свой источник правды в
   чекауте;
2. константы из раздела «Что уедет в `.grace/project.md`» — дописать в конфиг;
3. карточки — скиллом **graceboard-card**, `--origin skill` (в режиме Гермеса —
   `agent`, см. `hermes.md`), по одной на каждый блок раздела «Карточки». Все поля
   брифа — флагами `gb card`, не пересказом в описании. Хвосты из реестра карты
   **берутся с доски** по id из Ш0b, а не создаются заново.
   **Создавай строго в порядке исполнения**: очередь
   доски FIFO по порядку создания *карточек*, и это единственный рычаг порядка между
   прогонами — `dependsOn` за границу своего плана не работает;
4. **сверка** — `gb card` с exit-кодом 3 означает неполный бриф, доска откажет в
   диспатче: чини сразу, не на preflight. Затем
   `gb.mjs board --project X --column backlog` — ровно N карточек в нужном порядке;
5. `node ~/.claude/bin/gb.mjs preflight --project X --card <id> …` — блокеры и жёсткий
   пол до запуска, а не после;
6. прогон(ы) — скиллом **graceboard-run**. Политику релиза из плана передавай
   флагами `--pr / --merge / --deploy`, **сверившись с шапкой**
   `head -20 ~/.claude/bin/gb.mjs`: неизвестный флаг `gb` не отвергает, а молча
   игнорирует. Флага в шапке нет → политика остаётся строкой плана и исполняется
   человеком. Не передал ничего → доска возьмёт `deploy_policy` из
   `.grace/project.md`, затем дефолт `always / manual / off`;
7. карту обнови: статус этапов, вошедшие deferred, решения, закрытые при утверждении
   (с датой).

## Правила нарезки этапа на карточки (Ш2b)

### Ось разреза — вертикальная. Это правило старше всех остальных

**Карточка — сценарий целиком: модель + сервис + эндпоинт + экран, которые его
замыкают.** Не слой. Разрез по слоям («сначала модели, потом API, потом фронт»)
выглядит аккуратно и стоит дороже всего:

- слои выстраиваются в **линейную цепочку** `модель → сервис → API → клиент → UI`, а
  доска исполняет **WIP=1**: календарь этапа становится суммой карточек, не максимумом;
- разрез проходит **сквозь одни и те же файлы** — соседние карточки правят один сервис,
  один роутер, одни локали, кладут по миграции подряд. Каждая платит полный прогрев
  контекста, чтобы прочитать то же самое заново;
- ни одну карточку **нельзя предъявить** — до последней в цепочке нет работающего
  сценария, а `acceptance` вырождается в «типы сходятся».

**Карточка — не минимальный кусок работы, а минимальный кусок, который имеет смысл
принимать отдельно.** Внутри карточки конвейер сам раскладывает работу на волны
`t1/t2/t3` — в одной сессии, на прогретом контексте, практически бесплатно. Всё, что
вынесено на уровень карточки, платит три полные сессии (`ask-functional`,
`ask-architecture`, `build`); всё, что осталось волной внутри, — не платит почти ничего.
Поэтому **сомневаешься между «две карточки» и «одна карточка в две волны» — бери
волны** и выпиши их в `description` карточки как t1/t2/t3.

Три запрета, каждый проверяется до создания карточек:

1. **Пересеклись `files[]` — это одна карточка.** Не «очередь разрулит», не «они же
   про разное»: общий файл означает, что разрез прошёл сквозь одну работу.
2. **Линейная цепочка длиннее 3 карточек запрещена.** Получилась — нарезка сделана по
   слоям, переразрезать. Допустимая форма графа — веер: 1–2 корня, остальные листьями.
3. **Карточка меньше ~200 строк или ≤ 2 файлов — не карточка**, а волна внутри
   соседней. Фиксированные накладные (≈5 минут и две ask-сессии) съедят её целиком.

### Когда этап всё-таки делится на фазы

Фазы `домен` / `поверхности` — **не обязательный шаг, а инструмент для одного случая:
один домен обслуживает две и более поверхности** (два кабинета, две роли, экран +
внешний потребитель контракта). Тогда контракт нельзя вывести из одного экрана, и он
выносится в доменную карточку вперёд. Между фазами гейт: контракт заморожен; если в
проекте есть кодогенерация клиента из контракта — она прогнана.

**Одна поверхность на домен → фаз нет**, домен и экран живут в одной вертикальной
карточке. Это обычный случай, а не исключение.

### Правила для доменной части

Работают и внутри вертикальной карточки (как граница её волн), и как правила фазы
«домен», если фазы понадобились.

1. **Одна связная модель домена + инварианты + тесты + эндпоинты = одна карточка**
   (связность по цели, а не по числу таблиц) — **вместе с поверхностью, если она
   одна**: тогда фазы «поверхности» у этого домена нет.
2. **Внешняя интеграция — всегда отдельная карточка** (рассылка, хранилище, KMS,
   антивирус, конвертер). Признак: тянет обвязку — ретраи, шаблоны, локализация,
   карантин, повторная отправка.
3. **Машина состояний или инвариант безопасности — отдельная карточка** (тип `backend`,
   либо `foundation`, если это каркас/схема: разметка grace идёт из типа).
4. Потолок: **≤ 3 новые сущности, ≤ 1 внешняя интеграция, ≤ 1 машина состояний.**

### Правила для поверхностей

1. **1 маршрут = 1 карточка. Экран собирается целиком, никогда по частям.** Вкладки
   внутри маршрута — часть карточки. Транспорт, типы и клиент API, которые нужны
   только этому экрану, — тоже часть карточки, а не отдельная «карточка-подготовка».
2. **Один экран в двух разделах/ролях = две карточки** (разные маршруты): первая по
   критпути делает фича-компоненты, вторая наследует их через `dependsOn`.
3. **Модалка с собственным макетом** — своя карточка, если открывается с двух и более
   экранов; иначе часть карточки своего экрана.
4. **Добавка на принятый экран** (сданный в предыдущем этапе) — отдельная карточка.
5. **Generic UI-kit — отдельная карточка до всех экранов.** Фича-компоненты так не
   выносятся: они рождаются внутри первого экрана, который их требует.
6. **Экран не влезает в такт** → режь **по полноте**, не по частям экрана: сначала
   экран целиком в базовой полноте (все блоки, данные настоящие), обогащение —
   отдельной карточкой следующего этапа. Другого способа разрезать экран нет.

### Потолки — проверить перед созданием карточек

Коридор двусторонний: и «слишком крупно», и «слишком мелко» — дефект нарезки.

| | Пол (мельче — склей) | Цель | Потолок (крупнее — режь) |
|---|---|---|---|
| Работа агента | 8 мин | **20–30 мин** | 35 мин |
| Файлов | 3 | 8–15 | 20 |
| Строк диффа | ~200 | 600–1500 | ~2000 |
| Поверхностей | 1 | 1–2 | 3 |
| Карточек на этап | 3 | **3–5** | 6 |
| Обращений к модели | 80 | **150–250** | 300 |

- **Поверхность** = экран, модалка с макетом, доменная сущность со своим хранилищем,
  внешняя подсистема. 4+ в одной карточке → режь.
- **Верхний потолок держит контекст, а не терпение**: build-сессия крупной карточки
  подходит к ~150k контекста, за ним компакт и потеря качества. Нижний держит
  накладные: карточка стоит трёх сессий независимо от размера.
- **Обращения к модели — тот же коридор с другой стороны.** Меньше 80 — карточка не
  окупает три сессии своего цикла; больше 300 — это уже не работа, а круг
  verify → implementing, по которому бьёт предохранитель доски (A1.1). Считать
  вручную не нужно: доска пишет метрики прогона в `plan.result.metrics`.
- **Этап шире 6 карточек — это два этапа**, а не длинный прогон.
- **Тест на хвост:** «что из заявленного заведомо не влезет?». Длиннее двух пунктов →
  карточка крупная; ≤ 2 пунктов → **сразу** в `outOfScope` с адресом («→ этап F»).
- **Scope перечисляет, а не пересказывает**: есть ссылка «детали §X» — выпиши из §X,
  что берётся и что не берётся.
- **`description` — 2–4 кБ самодостаточного текста, не ссылка** (лимит поля 50000).
- **Заметки встреч слей в план-файл до нарезки** (иначе конфликт «макет vs заметки»).

Откуда взяты пороги — `reference.md`.

## Тип карточки — вместо покарточных ручек

На карточке ОДНО поле исполнения — `--type`. Строгость разметки, кто пишет код, режим
сборки и порог предохранителя доска берёт из своей таблицы в момент диспатча (константа
доски, `FUNC_cardType` в `server.js`; проект правит клетку через `.grace/project.md →
overrides` только с указанием причины).

| type | что это | разметка | кодер | режим | порог A1.1 |
|---|---|---|---|---|---|
| `backend` | серверная логика, доменный слой, машина состояний | grace | обычный | inline | ×1.0 |
| `screen` | экран / UI-слайс | grace | **фронтендер (Opus + frontend-design)** | hybrid | ×0.8 |
| `integration` | стык с внешней системой | grace | обычный | inline | ×1.0 |
| `foundation` | каркас, схема данных, миграции, UI-kit | grace | обычный | inline | ×0.7 |
| `fix` | правка по конкретному провалу (заводит обычно сама доска) | **off** | обычный | inline | ×0.5 |

**Правило смешанной карточки — тип по ДОМИНИРУЮЩЕЙ работе.** «Экран» — это
вертикальный слайс с UI **вместе с мелкой серверной обвязкой**, которую он читает
(эндпоинт, лоадер, экшн): такая обвязка не повод заводить вторую карточку и не повод
называть карточку бэкендом. Честные 50/50 фронт+бэк — это **две карточки**, связанные
через `contract`: бэкенд публикует контракт, экран получает его готовым через
`dependsOn` и не переспрашивает.

`fix` вручную почти не нужен: карточки починки заводит сама доска — по красной приёмке
прогона (A2.1) и по красному пост-мерж CI (A4.3).

Конкретные инварианты карточки берутся из `.grace/project.md`, а не выдумываются.

## Структура план-файла

Один файл = один этап = один прогон.

```markdown
# <Этап>: <цель прогона>

## Место в карте              ← ссылка на 00-<модуль>-map.md: какой сценарий замыкает,
                                 какой контракт отдаёт дальше, какие deferred входят
## Реестр источников          ← Ш1: источник · приоритет · что устарело · как разрешено
## Карточки                   ← блок на карточку: тема · суть · волны t1/t2/t3 ·
                                 НЕ входит · приёмка · контракт · файлы · зависимости.
                                 Домен обслуживает ≥2 поверхностей → подразделы
                                 «фаза домен» / «фаза поверхности», иначе одним списком
## Граф                       ← DAG в порядке исполнения + длина макс. цепочки (≤3)
## Политика релиза            ← pr / merge / deploy + обоснование
## Открытые вопросы           ← из Ш4: 2–3 варианта, дефолт помечен
## Что уедет в .grace/project.md   ← константы, найденные по ходу
```

Объём в один этап → разделы карты («что готово / чего нет / модель данных») идут в
этот же файл вместо «Места в карте».

## Строгость по автору карточки

`--origin skill` → доска проверяет строго: `outOfScope`, `acceptance`, `sources`
непусты, `contract` заполнен **или** явно `TBD`, иначе отказ в диспатче. У
`origin: human` требований нет.

`contract` — три состояния: **заполнен** (агент следует дословно) · **`TBD`** (контракт
проектируется в этой карточке, агент публикует его в `result.contract`, зависимые
получают при диспатче) · **пусто** — только для `origin: human`.

## Ответы человека

**Ответ, являющийся константой проекта, уезжает в конфиг, а не остаётся в карточке** —
он спрашивается один раз в жизни проекта, и владелец обоих файлов конфига — этот скилл.
Адрес стенда, id чата, команда выкатки, абсолютный путь → `.grace/local.md` (в
`.gitignore`); остальное → `.grace/project.md` (коммитится).

## Чего скилл не делает

- не создаёт карточки до утверждения (Ш7) — ни одной, ни «черновой»;
- не правит уже задиспатченные карточки (доска отдаст 409);
- не решает за человека бизнес-вопросы и объём выноса — выносит на Ш7;
- не режет экран на части и не приносит с собой предметную область.
