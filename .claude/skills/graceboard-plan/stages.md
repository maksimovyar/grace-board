# Нарезка на этапы и карта модуля

Читается на Ш2a, когда этапов **два и больше**. Один этап — этот файл не нужен.

Содержание: инвентаризация репозитория (Ш1b) · порядок этапов · состав карты ·
правила нарезки на этапы · deferred · сколько прогонов выносить.

## Ш1b. Инвентаризация репозитория

Разделы карты «что уже готово» и «чего нет» пишутся по коду, а не по памяти сессии.
Запусти **два параллельных субагента `Explore`** одним сообщением:

1. «что из требуемого уже реализовано в этом репозитории и где именно» — модели,
   эндпоинты, экраны, инфраструктура (аутентификация, аудит, шифрование, очереди);
2. «где живут макеты, требования, миграции, тесты, и по какому образцу они сделаны».

Их выход = разделы «Что уже готово» и «Чего нет». Пропуск шага стоит дорого: главная
ценность карты — защита фундамента от переписывания, а её даёт только инвентаризация.

## Два уровня файлов

**Карта** `docs/plans/00-<модуль>-map.md` живёт долго и обновляется после каждого
прогона. **План прогона** `docs/plans/<этап>.md` — на один этап.

## Порядок этапов = порядок порождения данных

Выпиши цепочку жизненного цикла главной сущности продукта и сделай каждое звено
этапом. Звено не может начаться, пока не существует предыдущее — это и есть
зависимость этапов, а не вкусовщина. Цепочку бери из модели данных, не из структуры UI.

После цепочки идут два класса этапов, которые своих данных **не порождают**:
- **этапы-роли** — новый раздел под роль поверх готовых данных: реюз моделей и экранов
  в новом скоупе;
- **этапы-надстройки** — сводки, календари, уведомления, поиск, AI: читают накопленное.

**Технический фундамент** (UI-kit, каркас, инфраструктура) — **нулевым этапом, перед
первым**, а не «параллельно»: доска исполняет WIP=1 на проект, параллельных рукавов
нет. Если фундамент мал, он не отдельный прогон, а первые карточки первого этапа.

## Состав карты

| Раздел | Зачем |
|---|---|
| Решения, закрытые до планирования (**с датой**) | вопрос, закрытый письменно, не всплывёт в рантайме |
| **Что уже готово** — переиспользуем, не переписываем | защита фундамента |
| **Чего нет** — пишем с нуля | честная граница объёма |
| **Модель данных**: новые сущности целиком | питает `contract` карточек; фиксируется на уровне модуля |
| Таблица этапов: `Этап · Название · Роль/раздел · Зависит · Статус` | DAG уровня этапов |
| **Критический путь** сквозь карточки всех этапов | это и есть порядок создания карточек на Ш8 |
| `rigor` по этапам с обоснованием | правило ниже |
| **Реестр deferred** с привязкой к будущему этапу | правило ниже |
| Что вынесено за границу объёма (**с датой**) | `outOfScope` уровня модуля |

Карта утверждается тем же гейтом Ш7. После каждого прогона обновляется: статус этапа,
новые записи в реестре deferred, закрытые решения с датой.

## Правила нарезки на этапы

1. **Этап = один сквозной сценарий, который можно предъявить.** Граница там, где
   сценарий замыкается: приёмка прогона гоняет сценарии из `acceptance` всех карточек,
   и без замкнутого сценария проверять нечего.
2. **Размер 6–12 карточек ≈ 3–6 часов конвейера** (такт карточки 20–30 мин, WIP=1).
3. **Граница этапа = граница заморозки контракта.** Следующий этап контракт предыдущего
   **потребляет**, а не переопределяет. Приходится переопределять — граница не там.
4. **Технический этап допустим** (UI-kit, инфра): сквозного сценария нет, приёмка —
   «собирается, типы проходят, showcase рендерится».
5. **Этап, порождающий данные, не смешивается с этапом, который их только читает.**
   Половина карточек создаёт сущности, половина строит поверх них сводки или кабинет
   роли — это два этапа, и второй зависит от первого.

## Deferred привязывается к этапу, а не копится

Хвост, поднятый прогоном, вносится в реестр карты с указанием этапа, в котором будет
сделан. **При сборке прогона этого этапа хвосты берутся с доски существующими
карточками, а не заводятся заново** — иначе получишь дубль планового и потеряешь
контекст, накопленный на карточке.

## Сколько прогонов выносить (Ш7)

Технические факты, на которых строится выбор:
- очередь доски **WIP=1 на проект**, порядок — FIFO по порядку создания карточек;
- **межплановых зависимостей нет**: `dependsOn` фильтруется по карточкам своего плана.
  Порядок между прогонами держится только порядком создания их карточек;
- карточка правится, **только пока она в Backlog и не задиспатчена** (иначе 409).

| Вынести | Плюс | Минус |
|---|---|---|
| **один этап** | правки следующих этапов по итогам первого; сбой не уводит вперёд неверную работу | возвращаться к скиллу после каждого прогона |
| **несколько** | автономный длинный прогон без человека | карточки поздних этапов ждут часами; правки невозможны |
| **все** | максимум автономности, вплоть до ночного прогона | сбой раннего этапа не остановит поздние |

Расклад по умолчанию, который приводишь человеку: **1–2 этапа — выносить все; 3+ —
выносить первый, дальше по итогам приёмки.** Исключение — этапы, независимые по
контракту: их можно выносить пачкой.
