Реализуй утверждённый проект из `docs/DESIGN-plan-skill-warden-config.md`
(проект `~/Projects/grace-board`, ветка `autodev/plan-run`).

## Что это за система

`grace-board` — локальная канбан-диспетчерская пайплайна grace-feature-dev.
Zero-dependency Node HTTP-сервер (`server.js`, ~2500 строк, без сборки, запуск
`node server.js`) + статический UI (`public/`), состояние в `data/board.json`
(в `.gitignore`). Порт 4317, только 127.0.0.1. Тестов в репозитории нет —
проверка ручная: поднять сервер, `curl` по API, прокликать UI.

Карточка доски порождает detached headless-ран `claude -p …` в целевом проекте.
Прогон (Plan Run) — несколько карточек с DAG зависимостей, общей интеграционной
веткой `autodev/plan-<id>` и режимом `ask`/`auto`.

## Читай первым делом

1. `docs/DESIGN-plan-skill-warden-config.md` — **это то, что нужно реализовать**.
2. `CLAUDE.md` — инварианты проекта.
3. `PLAN-RUN-ROADMAP.md` §4 (git-модель), §5.3 (AUTO и жёсткий пол), §6.1
   (манифест релиза) — проект на них опирается и в одном месте их меняет
   (см. §5 проекта: «PR всегда, мерж по политике» вместо «мерж делает человек»).
4. `docs/FIX-quota-exhaustion-resilience.md` — разбор смертей ранов по лимиту
   токенов; шаг 4 (агент-страж) закрывает описанное там.

## Основание (чтобы понимать, что оптимизируем)

Разбор прогонов 25–27.07 по DocsInside2 / Hermes / Лайти:
- КПД прогона 25% — 21.1 ч календаря при 5.2 ч чистой работы, 16 мин на карточку;
- 8 ч простоя на двух вопросах о границах объёма («в объёме C5?»);
- 3.6 ч на авариях исчерпания квоты (два ручных relaunch);
- 30 хвостов (`deferredSpawned`) за один прогон;
- 6 планов из 6 остались в `status: "running"`, `result: null`, архивированы руками.

## Инварианты — нарушать нельзя

- **Два режима, не замена.** Движок поддерживает И одиночную карточку
  (`planId: null`), И прогон. Путь одиночной карточки не меняется по поведению —
  на живой доске 86 карточек, большинство одиночные.
- **Новые поля модели — аддитивные, с дефолтами.** Изменения `data/board.json`
  forward-only. Старая карточка без новых полей обязана работать.
- **`origin` по умолчанию = `human`** для всех существующих карточек — это
  режим без проверок, значит миграция ничего не ломает.
- **Разметка GRACE** в новом и тронутом коде: идиома `// region … # endregion` +
  `## @`, как в `FUNC_detectDirectives` / `FUNC_spawnRun`.
- **Трейс — в существующий `DISPATCH_LOG`** (ndjson), отдельный `app.log` не заводим.
- UI-правки — на токенах `public/styles.css` (`:root`), без переопределения
  существующих классов; держать синхронно с `design/`, если трогаешь референс.

## Запреты

- Не переименовывать и не удалять существующие поля карточки.
- Не трогать живые карточки в `data/board.json` иначе как миграцией с дефолтами.
- **Перед любой миграцией состояния — `cp data/board.json data/board.json.bak.<шаг>`**
  (в репозитории уже есть такие бэкапы, следуй той же схеме именования).
- Не запускать раскатку конфигов по чужим проектам без явного «да» от человека
  (шаг 1 создаёт только шаблон и промпт-заготовку).
- Не менять `STALL_MS`, `ACTIVE_COLUMNS`, семантику колонок без нужды.

## Порядок работы

Шаги идут строго по очереди, **каждый — отдельный коммит с приёмкой**. После
каждого шага: подними сервер, проверь фактически (curl + UI), отчитайся человеку
одной короткой сводкой и переходи к следующему. Не делай два шага в одном коммите.

Если объём чата кончается — останавливайся на границе шага, а не посередине.

### Шаг 0 — `.gitignore`

Строка `.grace/local.md` в `.gitignore` **этого** проекта (для остальных проектов
это часть промпт-заготовки шага 1, не делай сам).

Приёмка: `git check-ignore .grace/local.md` возвращает путь.

### Шаг 1 — конфиг проекта

- Шаблоны `.grace/project.md`, `.grace/local.example.md` по §3.2–3.3 проекта.
- Чтение обоих в `compiledRequirements()` (`server.js:143`) — конфиг целевого
  проекта подмешивается в каждый ран. `local.md` перекрывает одноимённые ключи
  `project.md`; отсутствие `local.md` — не ошибка.
- Промпт-заготовка раскатки по проектам (§3.4) — положить в `docs/`, **не запускать**.

Приёмка: завести тестовую карточку в проекте с заполненным `.grace/project.md`,
убедиться по логу рана, что константы конфига попали в промпт.

### Шаг 2 — скилл `graceboard-plan`

Создать `~/.claude/skills/graceboard-plan/SKILL.md` по §1 проекта. Стиль и
структура — как у соседних `~/.claude/skills/graceboard-card/SKILL.md` и
`graceboard-run/SKILL.md` (фронтматтер `name` + `description` с триггерами,
раздел «Порядок действий», раздел соглашений).

Обязательно отрази: два такта с гейтом утверждения (Ш6–Ш8), структуру
план-файла `docs/plans/<slug>.md`, правила нарезки (§1.4 Ш2), симуляцию порога
эскалации (`server.js:846-853`), режим Гермеса (§1.6).

**Текст SKILL.md покажи человеку до того, как считать шаг завершённым** — он
хотел утвердить скилл лично.

Приёмка: скилл виден в списке скиллов; прогнан вхолостую на одном реальном
наборе требований — план-файл создан, карточки НЕ созданы.

### Шаг 3 — поля карточки

- Новые поля по §4.1: `outOfScope`, `acceptance`, `contract`, `sources`, `origin`.
  Аддитивно, с дефолтами; `origin` по умолчанию `human`.
- Валидация по `origin` (§4.2): для `skill|agent` отказ в диспатче при пустых
  `outOfScope`/`acceptance`/`sources` и незаполненном `contract`; для `human` —
  никаких требований.
- Состояния `contract` и **наследование по DAG**: карточка с `contract: TBD`
  пишет результат в `result.contract`, зависимые карточки получают его при
  диспатче (§4.1).
- `deferredSpawned` (`server.js:913-919`) — наследовать от родителя `sources`,
  `contract`, `requirementsLink`, `files[]`; создавать карточку черновиком, не
  диспатчить, пока черновик.
- UI: поля в форме создания и в карточке, бейдж `origin`, пометка черновика.
- Новые поля отдать агенту в промпте отдельными блоками (`outOfScope` — с
  формулировкой «это уже решено, не спрашивай»).

Приёмка: старая карточка без новых полей диспатчится как раньше; карточка с
`origin: skill` и пустым `acceptance` получает отказ; хвост создаётся черновиком
с унаследованными полями.

### Шаг 4 — агент-страж `board-warden`

Независим от шагов 1–3, можно делать раньше, если удобнее.

- API: `GET /api/health`, `POST /api/tasks/:id/pause|resume`,
  `POST /api/tasks/:id/note`, регистрация обработчика (§2.2).
- Событийный вызов: доска зовёт агента, когда супервизор собрался пометить
  `blocked`, либо карточка стоит в `asking`/рабочей станции дольше порога.
  **Никакого опроса доски агентом.**
- Описание агента с классификатором и таблицей действий (§2.3), запретами (§2.4),
  бюджетом 5 вмешательств на карточку в сутки.
- Локально и на VPS — один контракт, различаются `BOARD_URL` и канал уведомления.

Приёмка: смоделировать `crash-before-write` (карточка в `asking` с `questions: []`)
— страж классифицирует и перезапускает стадию; смоделировать `quota` — карточка
уходит в `paused`, а не в `blocked`.

### Шаг 5 — закрытие прогона

- Политика на входе прогона: `--pr`, `--merge`, `--deploy` в `gb.mjs run`
  (`~/.claude/bin/gb.mjs`) и в API `/api/plans`; дефолты из
  `.grace/project.md → deploy_policy`, иначе `always/manual/off`.
- Автофаза закрытия (§5.2): все карточки в `ready` → `verifying` → сборка
  `plan.result.releaseManifest` по правилам слияния §6.1 роадмапа → приёмка → PR.
- Приёмка прогона (§5.3): чистый чекаут интеграционной ветки, детерминированная
  часть (`typecheck`/`test`/`build` из конфига), затем функциональная — сценарии
  из `acceptance` всех карточек прогона + `manualChecks` манифеста;
  результат в `plan.result.acceptance` с evidence.
- PR всегда, тело автоматическое (§5.4), включая список хвостов.
- Ветвление по таблице §5.5. **Красная приёмка → деплоя нет никогда.**
  `stand.is_production: true` → деплой требует человека независимо от `autonomy`.
- `plan.status`: `running → verifying → done|failed`; архив — следствие закрытия.

Приёмка: прогон из двух дешёвых карточек проходит цикл до PR; при красной
приёмке PR уходит в draft и деплой не запускается.

## Как отчитываться

После каждого шага — короткая сводка: что сделано, чем проверено (команда и её
вывод), что осталось. Без пересказа кода, ссылки вида `server.js:143`.

Если по ходу выяснится, что решение из проекта не ложится на код — **не
переделывай проект молча**: опиши расхождение, предложи вариант, дождись ответа.
