> Открой новую сессию Claude Code **в проекте `~/Projects/grace-board`** и проработай эту задачу.
> Статус: **проблема зафиксирована, решение не финализировано** — ниже симптом, корень и направления
> лечения; выбрать подход и реализовать точечно.

Проект `~/Projects/grace-board` — локальный kanban-диспетчер `/grace-feature-dev`. Логика в `server.js`
(Node, без сборки, запуск `node server.js`). Состояние — `data/board.json`. Каждая карточка порождает
detached headless-ран `claude -p …` в целевом проекте (`spawnRun`, `server.js:632`).

---

## Симптом

Во время автономного прогона **исчерпание токенов/лимита Claude-подписки** роняет headless-раны на
полпути. Автономность этого не переживает:

- ран умирает в рабочей станции (`implementing`/`verifying`/`ask-*`) → карточка застревает;
- `autoheal` делает **один** relaunch — но лимит глобальный, поэтому повторный ран падает мгновенно так же
  → карточка уходит в **`blocked`** («авто-исцеление уже применялось и не помогло»);
- ран, умерший в `ask-functional` **до записи вопросов**, оставляет карточку в **`asking` с `questions:[]`**
  — тупик: супервизор не трогает `asking` (ждёт человека), а человеку отвечать не на что;
- при **возврате токенов нет авто-возобновления** — каждую застрявшую карточку приходится
  перезапускать вручную (`POST /api/tasks/:id/relaunch`), сериализуя по WIP=1 своим скриптом.

Итог: временный внешний лимит (само-восстановимый через время) выглядит как постоянная поломка и
требует ручного вмешательства.

## Корень проблемы (`server.js`)

1. **Смерть рана не классифицируется по причине.** `spawnRun` (`server.js:632`, `detached:true`+`unref`)
   пишет вывод в лог, но супервизор судит только по **liveness pid** и `STALL_MS` (`server.js:72`) —
   «жив/мёртв», а не «почему умер». Маркеры лимита (`claude -p` печатает про usage/rate limit; ненулевой
   exit) не читаются.
2. **`autoheal` — фиксированный 1 повтор** (`autoHealCount`), без backoff и без различия «временный лимит»
   vs «реальная ошибка». При глобальном лимите повтор бесполезен → `blocked`.
3. **`asking` без вопросов = мёртвый тупик.** `asking` исключён из `ACTIVE_COLUMNS` (`server.js:75-76`,
   «там ждём человека») — поэтому ран, умерший в ask-stage до записи `questions`, оставляет карточку
   в `asking` с `questions:[]`, и супервизор её не лечит (а человеку нечего отвечать).
4. **Нет авто-resume при снятии лимита.** Перезапуск — только ручной `/api/tasks/:id/relaunch`
   (`server.js:1392`, через `resumeRun` — resume работает). Нет пакетного «возобновить прогон» и нет
   пробы «лимит уже вернулся?».

## Направления лечения (выбрать/скомбинировать, не всё сразу)

1. **Классификатор смерти рана.** Перед autoheal читать хвост лога рана (+ exit-code) на маркеры лимита
   (`usage limit`, `rate limit`, 429-подобное). Вынести список маркеров в конфиг/константу.
2. **Статус `paused-quota`** (новый column вне `COLUMNS`-рабочих или флаг `card.pausedReason="quota"`)
   вместо `blocked` при детекте лимита. Семантика: «не сломано, ждёт сброса лимита».
3. **Авто-resume по расписанию.** Тик супервизора периодически пробует relaunch `paused-quota` карточек
   (проба доступности / экспоненциальный backoff / известное время сброса лимита). Уважать WIP=1.
4. **Отдельный счётчик quota-повторов**, не сжигающий `autoHealCount` — временный лимит не должен
   исчерпывать бюджет автолечения реальных багов.
5. **`asking` без вопросов при мёртвом pid = сбой, не HITL.** Детект `column=asking && questions:[] &&
   askStage=functional && pid мёртв` → авто-relaunch ask-stage, а не бесконечное ожидание человека.
6. **Детект глобального события.** Если ≥2 ранов умерли в узком окне (например < 60 c) — трактовать как
   инфра/quota-сбой (массовая пауза + авто-resume), а не как N независимых ошибок карточек.
7. **Пакетный resume прогона.** Endpoint/кнопка «возобновить прогон»: relaunch все не-`ready` карточки
   плана по одной (WIP=1). Сейчас это делается вручную + внешним watcher-скриптом.

## Ограничения

- Не ломать рабочий resume (`/relaunch` → `resumeRun`) и «развилки есть → человек → build».
- `column` — только из словаря `COLUMNS` (`server.js:91`); новый статус ввести аккуратно (или флагом на
  карточке, а не новой колонкой).
- `board.json` — единственный источник истины; супервизор читает `readBoard()` каждый тик — сохранить.
- Точечные правки, не переписывать `server.js` целиком.

## Проверка

- `node --check server.js`.
- Мок `claude` (через `GRACE_AUTORUN`/`dryrun_gfd/`), который завершается с сообщением про usage-limit:
  карточка должна уйти в `paused-quota`/флаг, **не** в `blocked`; авто-resume срабатывает после «снятия».
- Сценарий: 2 карточки умирают в окне < 60 c → массовая пауза, не 2 отдельных `blocked`.
- Сценарий: ран умер в ask-functional до записи вопросов → карточка НЕ виснет в `asking` навсегда.

## P.S. Смежная мелочь — рестарт доски на macOS ломается на `setsid`

При перезапуске сервера командой вида `nohup setsid node server.js &` на **macOS** падает
(`setsid: No such file or directory` — `setsid` нет в базовом macOS), сервер не стартует, доска лежит.
Правильно: `nohup node server.js &` + `disown` — detached достаточно (раны и так `spawn … {detached:true}`
+ `unref`). Проверить `install.sh` / `README.md` / любые доки и подсказки на предмет `setsid` и убрать его
из инструкций рестарта под macOS.
