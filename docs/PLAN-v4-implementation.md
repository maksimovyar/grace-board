# План реализации v4 «пульт прогонов»

Опорный прототип: [design/board-v4-a-track.html](design/board-v4-a-track.html).
Разбор и замеры: [docs/UX-REVIEW-v4.md](docs/UX-REVIEW-v4.md).

Принят вариант **A** плюс три решения, принятых в обсуждении 2026-08-01:

1. **Правило зоны «Требует меня»**: строка попадает туда, только если работа
   **стоит** И снять остановку может **только человек**. Оба условия сразу.
2. **`merge: manual` — это финал, а не ожидание.** Собран PR → прогон закрыт.
   Доска не ждёт, не опрашивает и не показывает гейт. Ждать имеет смысл только там,
   где доска обещала сделать сама и не смогла.
3. **Конвейером можно управлять, не убивая его**: стоп-кран с тремя положениями,
   где у каждого сказано, что успеет доиграть и чего это будет стоить.

---

# Постановка

## Цель

Доска перестаёт быть «канбаном задач вообще» и становится пультом автономного
конвейера. Человек, открыв её, отвечает на один вопрос — **нужен ли я сейчас** — и на
второй, если открыл сам: **где оно едет и когда встанет**. Дизайн-язык не меняется:
палитра, шрифты, лампы станций, рычаг запуска остаются.

## Что входит в объём

- Board-level стоп-кран: `after-stage` · `after-run` · `now`, с честной подписью цены (Ш0).
- Закрытие прогона: `merge: manual` → терминальный `pr-ready`; `awaiting-merge`
  остаётся только как `merge-failed` для сломанного авто-пути (Ш1).
- Политика релиза (`pr` · `merge` · `deploy`) в мастере запуска + строка вердикта (Ш2).
- Архивация карточек закрытого прогона (Ш3).
- Зона «Требует меня» по правилу «стоит И только человек» (Ш4).
- Полка закрытого: финальный статус, приёмка, PR с пометкой черновика (Ш5).
- Прогон как трек: свёрнутый/развёрнутый, голова, очередь строками, флажки остановок,
  **проект первым чипом в шапке прогона** (Ш6).
- Карточка: три размера, полоса цикла с фактическими длительностями, возраст на
  станции, AUTO-журнал, состояния «запускается» и «между этапами» (Ш7).
- Схлопывание восьми станций в четыре и снятие горизонтального скролла (Ш8).
- Хвосты: прокрутка не сбрасывается, поиск, плотность, `.hint`, обратимое удаление (Ш9).

## Не входит в объём

Решено, не переспрашивать:

- **Переупорядочивание этапов в запущенном прогоне** и вставка карточки в него —
  это правка модели (`plan.cardIds` + `dependsOn`), отдельная задача.
- **User story как объект** (история + сводная приёмка на уровне прогона) — в v4
  представлена только прогнозом остановок на треке.
- **Опрос состояния PR через GitHub** и кнопка «уже смержено» — не нужны: при
  `merge: manual` PR это финал, доска ничего не ждёт.
- **Смена дизайн-языка** — переделываем информационную архитектуру и плотность, не скин.
- **Варианты B и C** — отвергнуты, прототипы остаются только как контекст решения.
- **Возобновление контекста агента** — невозможно by design: каждый этап это отдельный
  `claude -p`, продолжение идёт через записанное состояние (Ш0.1).

## Приёмка

Проверяемые пункты, по одному на строку:

1. При `merge: manual` прогон после создания PR получает `closeStatus: "done"`,
   `closeStep: "pr-ready"`, появляется на полке и **не появляется** в зоне «Требует меня».
2. `merge-failed` возникает только при `merge: auto` (упавший мерж или отсутствие PR)
   и даёт ровно одну строку в зоне.
3. Кнопка «Финальный PR в main →» удалена; на её месте ничего не обещает действия.
4. Мастер отправляет `policy` в `POST /api/plans`; выбранное видно в `plan.policy`
   в `data/board.json` сразу после запуска.
5. Строка вердикта в мастере меняется при каждом переключении и называет три
   исключения: без автомержа деплой не сработает · боевой стенд спросит · красная
   приёмка отменяет всё.
6. `board.hold` переживает перезапуск сервера и снимается только человеком.
7. При `hold: "after-run"` в `DISPATCH_LOG` нет `queue-dispatch` для карточек других
   прогонов; текущий прогон доходит до конца и закрывается по своей политике.
8. При `hold: "after-stage"` не стартует ничего; активный этап доигрывает и доходит
   до своей станции.
9. «Оборвать этап сейчас» шлёт `SIGTERM` живому `runPid`; после снятия удержания
   `resumeRun` поднимает карточку с самой дальней **записанной** точки.
10. Подпись пункта «Оборвать этап сейчас» называет цену по текущей фазе (арх-фаза
    заново · откат к зелёному коммиту · проверка заново).
11. `DELETE /api/plans/:id?withCards=1` помечает `archived: true` карточкам прогона
    в `ready`; они исчезают из колонок и остаются видны в прогоне на полке.
12. Зона «Требует меня» пуста на данных, где конвейер идёт сам; счётчик в шапке
    считает только её.
13. Вопросы по функционалу и решения по архитектуре — две разные строки зоны.
14. Чип `🤖 N` открывает журнал авто-решений: вопрос → выбор → обоснование.
15. В голове карточки полоса цикла с фактическими длительностями из `card.history`.
16. В шапке прогона первым чипом стоит проект.
17. На окне 1440×900: `board.scrollWidth <= board.clientWidth`, вложенных областей
    прокрутки нет.
18. Путь одиночной карточки не изменился: рычаг, дроп-зоны, `POST /api/tasks`
    работают как до доработки.

## Контракт данных

Всё аддитивное, forward-only; старые данные читаются правилом, миграций нет.

```
board.hold      : "off" | "after-stage" | "after-run"    // новое, дефолт "off"
card.archived   : boolean                                 // новое, дефолт false
plan.closeStep  : + "pr-ready" | "merge-failed"           // новые значения
                  // "awaiting-merge" остаётся только для чтения старых прогонов:
                  //   policy.merge === "manual" → читать как "pr-ready"
                  //   иначе                     → читать как "merge-failed"
plan.policy     : { pr, merge, deploy }                   // поле есть; начинает
                                                          // приходить из мастера
```

Поля, которые уже есть и начинают использоваться в UI без изменения формата:
`card.history` (длительности фаз), `card.result.autoDecisions` и `card.archDecisions`
(AUTO-журнал), `card.lastColumnChangeAt` (возраст на станции), `plan.project`
(чип проекта).

## Ш0 · Стоп-кран: дать доработать и встать

**Боль.** Сегодня остановить конвейер нечем. Есть пауза одной карточки (`card.paused`,
её ставит страж) — и всё. «Пусть текущий прогон дойдёт до конца, а следующий не
начинается» сделать нельзя никак, кроме как убить сервер.

**Три разных «стоп», и путать их нельзя** — они отличаются тем, что успеет доиграть:

| Положение | Что доигрывает | Когда встанет |
|---|---|---|
| `after-stage` | текущий этап | ~одна длительность этапа |
| `after-run` | весь текущий прогон, включая закрытие | оставшиеся этапы |
| `now` | ничего — текущий этап на паузу | сразу |

**Точка в движке ровно одна.** Все запуски проходят через `scheduleQueued`
([server.js:578-592](server.js#L578-L592)), и там уже стоит готовый прецедент — ранний
выход по лимиту подписки: `if (quotaOpen(board)) return false` ([server.js:582](server.js#L582))
с комментарием «очередь просто держится, порядок сохранён». Удержание — точно такой же
выход, только по флагу человека.

**Делаем.**

- `board.hold: "off" | "after-stage" | "after-run"` — рядом с `board.autonomy`,
  ставится через `PATCH /api/settings` ([app.js:256-262](public/app.js#L256-L262) —
  там уже есть готовый вызов для `autonomy`).
- В `scheduleQueued`:
  - `hold === "after-stage"` → `return false` (полный аналог quota);
  - `hold === "after-run"` → пропускать карточки, чей `planId` **не** равен плану,
    который сейчас держит слот проекта. Этапы текущего прогона продолжают ехать,
    всё остальное ждёт.
- `now` — **требует SIGTERM, одного `paused` мало.** Сегодня пауза не останавливает
  работу: процесс никто не убивает (единственный `process.kill` — watchdog по зависанию,
  [server.js:2078](server.js#L2078)), а `syncFromPipeline` перестаёт зеркалить карточку
  (`if (card.paused) continue`, [server.js:1916](server.js#L1916)). То есть агент
  продолжает писать код, а доска показывает «на паузе». Значит `now` = `process.kill(card.runPid, "SIGTERM")`
  + `paused` + `hold: "after-stage"`.
- `planCloseTick` **не** трогаем: закрытие прогона — это не новая работа, а завершение
  начатой. При `after-run` прогон обязан дойти до PR по своей политике.
- Удержание переживает перезапуск сервера (лежит в `board.json`) и снимается только
  человеком — само не рассасывается.

**UI** (реализовано в прототипе, функции `renderHold` / `brakeMenuHTML`):

- кнопка `⏸ Остановить` в шапке → меню из трёх пунктов, у каждого сказано, что
  доиграет и **когда примерно встанет** — оценка считается из фактических длительностей
  закрытых этапов этого прогона (`avgStageMin`), а не выдумывается;
- взведённое удержание — полоса под шапкой: что доигрывает, сколько осталось,
  кнопки «Встать сейчас» и «Отменить». Тон синий: пауза ≠ поломка;
- этапы, которые не стартуют из-за удержания, пишут `⏸ не стартует · удержание`
  вместо `⏳ слот проекта занят` — зависимость (`🔒 ждёт S2`) важнее и показывается первой;
- строка «Никто не ждёт» меняется на «Конвейер доигрывает и встанет», чтобы зелёная
  зона не обещала движения, которого не будет.

**Проверка.** Взвести `after-run` при живом прогоне: текущий доходит до конца и
закрывается, второй прогон остаётся в очереди, `DISPATCH_LOG` не пишет `queue-dispatch`
для его карточек.

### Ш0.1 · Что переживает обрыв, а что нет

Это надо знать, чтобы честно подписать кнопку. **Контекст процесса не переживает
ничего**: каждый этап — отдельный `claude -p <prompt>`, detached, без `--continue` и
`--resume` ([server.js:1335](server.js#L1335)). Промпт собирается заново при каждом старте.

Переживают три носителя:

| Носитель | Что в нём |
|---|---|
| `data/board.json` | `answers`, `archDecisions`, `askStage`, `column`, `history` |
| `<проект>/.grace-feature-dev/<slug>/board.json` | состояние прогона: та же тройка глазами самого прогона |
| git + файлы | коммиты `green(<cardId>): …` в интеграционной ветке, `DevelopmentPlan.md`, логи |

Возобновление собирает `resumeRun` ([server.js:1872-1901](server.js#L1872-L1901)):
берётся **самая дальняя достигнутая точка** и запускается заново ровно один из трёх
промптов —

- есть `archDecisions` или `askStage === "done"` → **сборка** (`implementing`),
  в промпт подмешивается RECOVERY: «продолжи с самого дальнего зелёного чекпоинта,
  `git log --oneline` → `green(<cardId>)`, фичу заново не начинай»;
- есть `answers` / `askStage === "functional-done"` → **арх-фаза заново**;
- иначе → **блок 1 заново**.

Отсюда цена обрыва по фазам — её и показывает пункт меню:

| Оборвали на | Что теряется | Что остаётся |
|---|---|---|
| `asking`, блок 1 | разведка и формулировки вопросов | постановка карточки |
| `asking`, арх-фаза | варианты решений, которые агент готовил | **ответы блока 1**, постановка, контракты от предыдущих этапов |
| `implementing` | всё, что не закоммичено как `green(...)` | последний зелёный коммит |
| `verifying` / `reviewing` | прогон проверки | код на месте |

Арх-фаза кода не пишет, поэтому её обрыв стоит минут работы агента и токенов —
не отката. Обрыв сборки дороже: откат к последнему зелёному коммиту.

Механизм не новый: ровно так уже работает восстановление после лимита подписки
([server.js:1833-1838](server.js#L1833-L1838)) — там та же `resumeRun` и тот же
RECOVERY-блок. Стоп-кран переиспользует проверенный путь, а не заводит второй.

## Ш1 · Закрытие прогона: `merge: manual` — финал

**Сейчас.** Ветка `pol.merge === "manual"` ставит `closeStatus: "done"`,
`closeStep: "awaiting-merge"` ([server.js:1157-1161](server.js#L1157-L1161)) с текстом
«Приёмка зелёная — готово к мержу». В это же состояние падают ещё два случая:
`merge: auto` без PR ([server.js:1163](server.js#L1163)) и провалившийся автомерж
([server.js:1181](server.js#L1181)). Три разные ситуации — одно состояние.

**Делаем.**

- Ввести `closeStep: "pr-ready"` — терминальный: `closeStatus: "done"`, `archived`
  не трогаем (архивация рельса — отдельное решение человека, см. Ш5).
  Текст: «Прогон закрыт: PR собран, мерж за тобой (политика прогона)».
- `awaiting-merge` оставить **только** для сломанного авто-пути и переименовать в
  `merge-failed`, чтобы имя не врало: «Автомерж не прошёл: <причина>».
- `awaiting-deploy` не трогаем — это настоящий жёсткий пол
  ([server.js:1191-1200](server.js#L1191-L1200)).
- `CLOSE_STEP_RU` ([app.js:309-311](public/app.js#L309-L311)) — добавить `pr-ready`
  и `merge-failed`, убрать «ждёт твоей кнопки мерж».
- Кнопку «Финальный PR в main →» ([app.js:299](public/app.js#L299),
  [app.js:355-362](public/app.js#L355-L362)) — удалить. Она ничего не делала, а по новой
  модели и не должна: в manual доска уже всё сделала, в auto — сделает сама.

**Совместимость.** Прогоны, уже стоящие в `awaiting-merge` (сейчас такой один — A2-1),
подхватываются правилом: `closeStep === "awaiting-merge" && policy.merge === "manual"`
читается как `pr-ready`. Миграцию данных не пишем — правило в чтении, forward-only.

**Проверка.** Запустить прогон с `merge: manual` → после создания PR `closeStep`
становится `pr-ready`, рельс уходит на полку, в зоне «Требует меня» пусто.

### Ш1.1 · Лимит подписки во время закрытия не должен проваливать прогон

**Наблюдено вживую 2026-08-01.** Прогон «Услуги B+» (13dc2476) довёл все 7 этапов до
`ready`, вошёл в приёмку — и получил `closeStatus: "failed"` с единственной проверкой:

```
{ id: "run", title: "Ран приёмки не отчитался", status: "fail",
  output: "You've hit your limit · resets 3:20pm (Europe/Moscow)" }
```

То есть **прогон помечен проваленным из-за лимита подписки**, а не из-за кода. PR #6
остался черновиком, `closeStep: "closed"` — состояние терминальное, само не починится.

**Причина.** Механизм «лимит — это часы, а не поломка» (`FUNC_quotaStop`, S6) покрывает
только карточки: `detectQuotaStop` вызывается по `card.runLog`
([server.js:2094](server.js#L2094), [server.js:2157](server.js#L2157)). Фаза закрытия
свой вывод (`acceptance.out`) на эту сигнатуру не проверяет. `planCloseTick` умеет
только **не начинать** приёмку, когда окно лимита уже открыто
([server.js:1052](server.js#L1052) — там даже стоит комментарий «paint the run red for a
reason that has nothing to do with the code»). Но если лимит прилетел **в середине**
рана, его вывод читается как обычный провал проверки — ровно тот случай, который
комментарий обещает не допускать.

**Делаем.**

- В разборе результата приёмки прогнать `detectQuotaStop` по `acceptance.out` тем же
  вызовом, что и для карточек.
- Нашли сигнатуру → не `failed`, а ожидание: `closeStep` остаётся на `acceptance`,
  прогон встаёт до `quota.until`, приёмка перезапускается после сброса. Ровно так уже
  ведёт себя карточка.
- То же для `pr.out`, `merge.out`, `deploy.out` — они спавнятся тем же `spawnStep`
  и подвержены тому же.
- Прогонам, уже провалившимся так, нужна ручка «перезапустить приёмку» — иначе
  единственный выход из терминального `failed` это собрать прогон заново.

**Проверка.** Открыть окно лимита во время приёмки → прогон не переходит в `failed`,
а ждёт и переигрывает приёмку после сброса.

## Ш2 · Политика релиза в мастере запуска

**Сейчас.** Движок умеет всё: `merge: auto` дёргает `gh pr merge`
([server.js:1169](server.js#L1169)), `deploy: after-merge` запускает `stand.deploy_cmd`
из `.grace/local.md` ([server.js:1191-1215](server.js#L1191-L1215)),
`POST /api/plans` принимает `policy` в теле ([server.js:2330-2339](server.js#L2330-L2339)).
Но мастер её не шлёт — [app.js:820](public/app.js#L820) отправляет только
`project/goal/mode/stages/decisions`. Поэтому все шесть прогонов уехали с дефолтом
`{pr: always, merge: manual, deploy: off}`.

**Делаем.**

- [index.html:54-74](public/index.html#L54-L74) — на шаге 1 мастера блок «Политика
  релиза» с тремя сегментами: **PR** (`always`/`never`), **Мерж** (`manual`/`auto`),
  **Стенд** (`off`/`after-merge`/`ask`).
- [app.js:813-825](public/app.js#L813-L825) — `fireLaunch` кладёт `policy` в тело.
- **Строка вердикта** под переключателями — главное здесь. Одним предложением: чем
  прогон закончится и сколько раз остановит. Готовая функция — `policyVerdict()`
  в прототипе. Она же обязана называть исключения:
  - `merge: manual` + `deploy ≠ off` → «деплой не сработает: без автомержа мержить нечего»;
  - `deploy ≠ off` → «если стенд помечен боевым, деплой всё равно спросит — жёсткий пол»;
  - всегда → «красная приёмка отменяет всё: PR останется черновиком».
- Значения по умолчанию берутся из `.grace/project.md → deploy_policy` того же проекта
  (сервер это уже делает, [server.js:2333](server.js#L2333)) — мастер должен показать
  именно их, а не свои, иначе человек увидит одно, а поедет другое.

**Проверка.** Собрать прогон с `merge: auto`, `deploy: off` → в `plan.policy` уезжает
именно это; по закрытию доска мержит сама.

## Ш4 · Зона «Требует меня»

Правило — в шапке этого документа. Реализация — функция `attention()` рядом с
`renderRails` ([app.js:341](public/app.js#L341)).

**Что входит:**

| Источник | Условие |
|---|---|
| `asking` + `questions.length` | вопросы по функционалу |
| `asking` + `archQuestions` без `archDecisions` | решения по архитектуре |
| `blocked` | и **не** `paused` — пауза по лимиту ждёт часы, а не человека |
| `autoFloorHeld` / `result.floor` | жёсткий пол |
| прогон `closeStep: merge-failed` | доска обещала смержить и не смогла |
| прогон `closeStep: awaiting-deploy` | боевой стенд |

**Что не входит:** лимит подписки (баннер, [app.js:328-340](public/app.js#L328-L340)),
`wardenPending` (решает агент), черновики-хвосты (ничего не стоит → счётчик в бэклоге),
`pr-ready` и `failed` прогоны (полка).

- Функционал и архитектура — **две разные строки**: разные вопросы, разная цена ошибки.
- Пусто → зелёная строка «Никто не ждёт. Конвейер идёт сам» + ближайшая остановка.
- Счётчик в шапке считает **только** эту зону.

**Проверка.** На текущих данных зона пуста, счётчик зелёный. Останов любой карточки в
`blocked` даёт ровно одну строку.

## Открытые вопросы

Границы объёма — в разделе «Не входит» выше. Здесь то, что предстоит решить **внутри**
принятого объёма:

- **Удержание на уровне одного прогона** (`plan.hold`) — в прототипе только доска
  целиком. Если проектов станет больше одного, «встать» захочется точечно.
- **Что делать с `hold`, когда прогон закрылся при `after-run`**: снимать
  автоматически (человек уже получил, что хотел) или оставлять взведённым до явной
  отмены. Склоняюсь ко второму — удержание не должно рассасываться само.
- **Черновики-хвосты**: из зоны убраны, но тихого счётчика в бэклоге ещё нет —
  формулировка появится вместе с Ш9.
