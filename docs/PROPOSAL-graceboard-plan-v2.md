Статус: **внедрено** (A1–A5, B1–B5, C3 — см. §7); открыты C1 и C2. v1 сохранена в
`docs/skills/graceboard-plan.v1/` (каталог `~/.claude/skills` не под git).

## 3. Диагноз v1

1. **Половина текста — обоснования, а не инструкции.** «Зачем он нужен» (5 строк),
   «Замеренная разница — карточки на 2.9–3.6 кБ дали 0–3 вопроса…» (4 строки),
   «Единиц работы меньше, потому что…» и т.п. Агенту для исполнения не нужно
   *убеждение* — нужно правило и число. Обоснования уже частично лежат в
   `reference.md`; в SKILL.md они дублируются.
2. **Горячий путь смешан с холодным.** Режим Гермеса (10 строк) нужен только при
   `origin: agent`; «карта модуля» (56) и «правила нарезки на этапы» (19) — только
   при ≥2 этапах; «сколько прогонов выносить» (19) — только на Ш7 и тоже при ≥2
   этапах. Итого 104 строки из 374 (28%) грузятся всегда, а нужны по условию.
3. **Нет чек-листа.** Процедура из 9 шагов с гейтом посередине подаётся сплошным
   текстом. Пропуск Ш4 или Ш0b ничем не ловится.
4. **Нет самопроверки плана перед гейтом.** Человек на Ш7 — первый, кто видит
   дырки. Дешёвая тройка проверок (покрытие / заглушки / стыковка контрактов) не
   формализована.
5. **Нет детерминированной валидации.** Все проверки — «спроси себя». Часть из них
   машинная: разделы файла на месте, у карточки непусты 5 полей, DAG ацикличен,
   пути в `files[]` существуют или помечены новыми, число карточек 6–12.
6. **Ровный тон везде.** Жёсткое («порядок Ш8», «гейт Ш7») и эвристическое («как
   резать конкретный экран») написаны одинаково — агент не различает, где мост над
   пропастью, а где открытое поле.
7. **Терминология плавает**: этап / прогон / план / плановый прогон / Plan Run — в
   одном файле, местами в одном абзаце.
8. **Ш8 п.5 расходится с кодом** (см. §1) — единственная фактическая ошибка.
9. **Инвентаризация репозитория ничем не подкреплена**: разделы карты «что уже
   готово / чего нет» скилл требует, но не говорит, откуда их взять.
10. **`reference.md` без оглавления** — 164 строки, при частичном чтении агент
    видит только начало.

Чего в v1 **не надо трогать** (это её сильные места, проверенные холостым
прогоном `docs/plans/quota-resilience.md`): два такта с гейтом; реестр источников с
письменным разрешением конфликтов; фазы «домен» → «поверхности»; правило «1 маршрут
= 1 карточка целиком»; потолок ≤3 поверхностей; порядок создания карточек = FIFO
критпути; ответы-константы уезжают в `.grace/project.md`; deferred берутся с доски.

## 4. Предложения

### Уровень A — обязательно

**A1. Починить Ш8 п.5.** Политика релиза записывается в план-файл и в описание
карточки текстом; флагами — только когда `gb run` их принимает. Формулировка без
даты (иначе устареет): «`--pr/--merge/--deploy` передавай, только если они
перечислены в шапке `head -20 ~/.claude/bin/gb.mjs`; иначе политика остаётся
строкой плана и исполняется человеком на мерже». Неизвестные флаги `gb` **не
отвергает — молча игнорирует**, поэтому проверка обязательна.

**A2. Убрать из SKILL.md все «почему».** Правило: строка остаётся, только если
меняет действие агента. Обоснования — в `reference.md` (там им и место).
Оценка: −70…90 строк без потери единого правила. **Это главный рычаг экономии
контекста**: снимается безусловно, в каждом прогоне (в отличие от B1 — см. там).

**A3. Чек-лист в начале процедуры** (паттерн Anthropic — агент копирует его в
ответ и отмечает):
```
Такт 1: [ ] Ш0 конфиг  [ ] Ш0b доска+дизайн  [ ] Ш0c готовность входа
        [ ] Ш1 источники  [ ] Ш2 нарезка  [ ] Ш3 поля  [ ] Ш4 симуляция ask
        [ ] Ш5 DAG+files  [ ] Ш6 самопроверка  [ ] Ш7 файл записан
ГЕЙТ:   [ ] человек утвердил
Такт 2: [ ] коммит плана  [ ] .grace обновлён  [ ] карточки  [ ] preflight  [ ] прогон  [ ] карта
```

**A4. Самопроверка перед гейтом (новый Ш6)** — три прохода, из `writing-plans`:
- **покрытие**: каждый пункт каждого источника → карточка или строка «НЕ входит»;
  непокрытых нет;
- **заглушки**: в плане нет «и т.п.», «аналогично N», «детали в §X» — `TBD`
  допустим **только** в `contract`;
- **стыковка**: поле/эндпоинт, который потребляет карточка B, порождается
  карточкой A и записан в её `contract`; расхождение имён = вопрос в рантайме.

**A5. Единый словарь, 3 строки, и дальше только эти слова.**
`этап ≡ прогон ≡ один план-файл ≡ ветка autodev/plan-<id> ≡ один PR` ·
`карточка` — единица внутри этапа · `фаза` — домен | поверхности.

### Уровень B — сильно рекомендуется

**B1. Вынос по условию использования, а не по теме.**

Механика, из-за которой «просто разбить на файлы» не работает: всегда в
системном промпте висят только `name` + `description`; тело `SKILL.md` при
срабатывании читается **целиком**; остальные файлы — обычным Read, когда агент до
них дойдёт. Значит

> экономия = строки, которые в **этом** прогоне не понадобились.

Вынос того, что читается всегда (шаблон план-файла, правила нарезки на карточки),
экономит ноль и платит лишним round-trip'ом плюс риском частичного чтения. Поэтому
делим по условию:

| Файл | Строк | Когда читается | Экономия |
|---|---|---|---|
| `SKILL.md` | ~180 | всегда: процедура Ш0–Ш8, жёсткие правила, нарезка **на карточки**, потолки, шаблон план-файла, чек-лист | — |
| `stages.md` | ~95 | Ш2a, **только если этапов ≥2**: карта модуля, нарезка на этапы, «сколько прогонов выносить» | реальная: прогон на один этап (частый случай — пример 2 в `reference.md`) не грузит 25% старого файла |
| `hermes.md` | ~30 | только при `origin: agent` | небольшая, но бесплатная |
| `reference.md` | ~165 | по требованию: пороги и два примера (+ добавить TOC) | уже вынесен в v1 |

Итог: прогон на **один этап** — ~180 строк вместо 374 (−52%); **многоэтапный** —
~275 (−26%). Бо́льшая часть выигрыша в обоих случаях даёт A2, а не разбиение.

Риск: агент не прочитает `stages.md` и порежет этапы по наитию. Снимается двумя
средствами — (а) на Ш2a стоит явное условие «этапов ≥2 → **СНАЧАЛА прочитай
`stages.md`**, без него нарезка на этапы неверна», (б) в SKILL.md остаётся
таблица-предохранитель с потолками (6–12 карточек на этап · ≤3 поверхности ·
1 маршрут = 1 карточка · внешняя интеграция отдельно · ≤3 сущности).

Отвергнутые варианты выноса: `plan-template.md` (нужен на Ш6 в каждом прогоне) и
`slicing.md` с правилами нарезки карточек (нужны на Ш2b в каждом прогоне) —
экономия нулевая, цена ненулевая.

**B2. Ш0c «готовность входа»** (из `brainstorming`): 4 признака — источники
названы и доступны; цель формулируется одним сценарием; известно, кто пользователь
и что он делает; ясно, чем меряется «готово». Провал ≥2 → **СТОП**, вопросы одним
пакетом, нарезка не начинается. Сейчас скилл честно пишет «вход = проработанные
материалы», но не проверяет этого.

**B3. Инвентаризация репозитория субагентами (Ш1b, только при ≥2 этапах).** Два
параллельных `Explore`: «что из требуемого уже реализовано и где» и «где живут
макеты, требования, миграции, тесты». Их выход = разделы карты «что готово / чего
нет». Иначе карта пишется по памяти, а «защита фундамента от переписывания» —
главная её ценность.

**B4. Вопросы — с вариантами, а не с «вариантом по умолчанию».** Каждый вопрос:
2–3 варианта + помеченный дефолт, ответ = буква. Человек на гейте отвечает в один
проход, не переписывая формулировки.

**B5. Постпроверка Такта 2.** После создания карточек: exit-код `gb card` (3 =
брифы неполны, доска откажет в диспатче) и `gb board --project X --column backlog`
— сверить, что создано ровно N карточек в нужном порядке. До `preflight`, а не
после.

### Уровень C — по желанию

**C1. `scripts/validate-plan.mjs`** — детерминированная проверка план-файла
(паттерн plan → validate → execute): обязательные разделы; у каждой карточки 6
непустых полей; `TBD` только в контракте; DAG ацикличен и покрывает все карточки;
6–12 карточек; пути `files[]` существуют или помечены новыми. Печатает список
проблем и коды выхода. Экономит модельные токены на самопроверке и не устаёт.

**C2. Три eval-сценария** (best practices: «build evaluations first»), чтобы v2
можно было сравнить с v1 не на глаз: (1) один этап без макетов — эталон уже есть,
`docs/plans/quota-resilience.md`; (2) модуль на 5+ этапов с картой и deferred с
доски; (3) `origin: agent` без человека. Метрики — те же, что в `reference.md`:
вопросов на карточку, хвостов на прогон, кБ описания.

**C3. Сжать `description` во фронтматтере** до ~450 символов, сохранив триггеры
(«разбей требования на этапы», «декомпозируй фичу», «карта модуля», «plan a run»).
Он грузится в системный промпт всегда, у всех скиллов сразу.

## 5. Как меняются формулировки (образцы)

**Ш0** — было 5 строк:
> Ш0. Прочитай `.grace/project.md` (и `.grace/local.md`, если есть) в целевом репо.
> Файла нет → остановись и предложи его завести (заготовка: …). Без конфига карточки
> поедут без констант окружения и без сквозных инвариантов проекта, и агент спросит
> про них в рантайме — ровно то, что чиним.

стало 2:
> **Ш0.** Прочитай `.grace/project.md` и `.grace/local.md` целевого репо.
> Нет → **СТОП**, предложи завести по `docs/PROMPT-grace-config-rollout.md`.

**Потолок описания карточки** — было 4 строки с числами исследования, стало 1:
> `description` — 2–4 кБ самодостаточного текста, не ссылка (лимит поля 50000).

**Блок «Зачем он нужен»** (5 строк) — из SKILL.md удаляется целиком, в
`reference.md` остаётся одной строкой: причина вопросов в рантайме — разрыв
контекста между сессией проработки и headless-раном.

**Тон.** Жёсткое — императивом и заглавными: «**НЕ создавай карточки до Ш7 — ни
одной, ни черновой**». Эвристическое — как эвристика: «экран не влезает в такт →
режь по полноте, не по частям экрана».

Ожидаемо было: A2+B1 → ~180 строк на одноэтапный прогон. **Факт после внедрения**
(замер, а не оценка) — см. §7: 250 строк / 21.2 кБ против 374 / 33.6 кБ. Оценка «~180»
была оптимистичной: она не учитывала, что A3/A4/B2/B5 добавляют в горячий путь ~30
строк нового текста (чек-лист, самопроверка, готовность входа, сверка Такта 2).
